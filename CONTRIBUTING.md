# Contributing to MDIO

> [中文要点](#贡献指南中文)

Thanks for taking the time to look at this project. Two things about how this
repository works are unusual, and they are deliberate. Please read them before
you write code or open anything.

## 1. Issues are the front door

**Issues are the only open contribution channel for now.** This project is new,
and pull requests are restricted to invited collaborators by a repository
setting, so a pull request opened from a fork will not be reviewed.

The way in is a high-quality issue: a bug with a minimal reproduction, or a
substantial design discussion. A maintainer may then invite you as a
collaborator.

If you are not invited yet, you are still useful: precise bug reports, minimal
reproductions, and documentation corrections are what move this project forward.

## 2. This repository is a published snapshot

The public repository is generated by exporting a curated subset of a private
development repository. Three consequences:

- A patch that lands here is **ported into the development line first**, then
  reappears in the next exported version. Your commit may be squashed or
  rewritten in that process; credit stays in the pull request and the release
  notes.
- If a change is merged here but never ported into the development line, the next
  export will overwrite it. That is why pull requests are restricted — it keeps
  the reconciliation honest.
- Feature work happens upstream of you. If you want a feature, open an issue and
  argue for it; if it is accepted it will appear in a future release.

## Reporting a bug

Use the bug report form under `.github/ISSUE_TEMPLATE/`. Either way, include:

- the MDIO version (`mdio --version`) and how it was installed (`uv tool install`,
  from a wheel, from source);
- the platform: Linux x86_64, Linux arm64, or macOS arm64. **Windows is supported
  through WSL2 only** — run inside WSL and keep the workspace on the Linux
  filesystem (`/home/...`), not on `/mnt/c`;
- the smallest markdown file or command sequence that reproduces the problem;
- expected versus actual output.

For security problems do **not** open an issue; see `SECURITY.md`.

## Development setup

The project has one supported entry point for every local action: the build grid.
`just` is a thin wrapper over it, and the grid is the source of truth.

Requirements:

| Tool | Version | Pinned by |
|---|---|---|
| Python | 3.14 | `uv sync --python 3.14` inside the grid |
| Rust | 1.98.0 | `rust-toolchain.toml` (rustup installs it on first build) |
| `uv` | any recent | — |
| Docker | any recent | UI bundle and the DuckDB extension build |
| `just` | optional | `justfile` (without it, call `runner.py` directly) |
| Node / pnpm | 24.21.0 / 11.28.5 | grid; the UI bundle runs inside a fixed Docker Node image, so a different host Node only produces a warning |

```bash
git clone https://github.com/cloudwalkerfre/MDIO.git
cd MDIO
just doctor     # or: python3 tools/build_grid/runner.py doctor
just install    # uv sync --python 3.14, then build the wasm engine
```

`just doctor` checks the toolchains and prints which are missing; fix those before
anything else.

## The build grid

Every target is declared in `build_grid.toml` (and `mdio_ui/build_grid.toml` for
UI targets). `just <name>` and `python3 tools/build_grid/runner.py <name>` are
equivalent; the latter also supports `--list`, `--dry-run` and `--json`.

| Target | What it does |
|---|---|
| `doctor` | check pinned toolchains and local prerequisites |
| `install` | `uv sync` plus the wasm engine build |
| `test` | `rust:test` + `py:test` |
| `test-rust` | `cargo test --workspace --lib` |
| `test-py` | Python suite, stable subset (`-m 'not slow'`, 4 workers, 300 s timeout) |
| `test-py-slow` | Python suite, only the `slow` marker |
| `test-omp` / `test-trinity` | heavy regression modes; run when you touch those areas |
| `check` | layer gates: UI layering and Rust import direction |
| `build-wasm` / `build-ui` | wasm engine, then esmx bundle into `mdio_py/src/mdio_py/web/client` |
| `build-arrow` | build the DuckDB extension (signed on macOS) |
| `wheel` | build the platform wheel (UI bundle + extension + env seed) |
| `verify` | install the built wheel and boot a local gateway |
| `release` | local release dry-run: `verify` + `test` |
| `serve` | start the gateway (`mdio serve`) |
| `demo` | Vite demo for the UI |
| `clean` | remove generated artifacts |

Use `runner.py --dry-run <target>` to see the dependency plan before running a
heavy target.

## Running tests

```bash
just test           # Rust + the stable Python subset
just test-py        # Python only
just test-rust      # Rust only
just check          # layer/import-direction gates
```

Three practical notes:

- **Isolate your real configuration.** Some tests read and write `~/.mdio`. Point
  `MDIO_HOME` at a temporary directory:
  ```bash
  MDIO_HOME="$(mktemp -d)" just test-py
  ```
  Set only `MDIO_HOME`. Do not override `HOME`: that also relocates the Cargo and
  rustup caches and triggers a full rebuild.
- **Heavy legs are opt-in.** `test-omp`, `test-trinity` and `test-py-slow` are not
  part of `just test`; run them when your change touches those areas. Tests that
  need a PTY, Docker, or network skip themselves when the prerequisite is absent.
- **If you keep a local `wt` workspace, be careful: it can be overwritten.**

## Building a wheel locally

```bash
just build-arrow    # DuckDB extension (needs a Rust toolchain; signs on macOS)
just build-ui       # wasm + esmx bundle (needs Docker)
just wheel          # assemble and build the wheel into dist/
just verify         # install that wheel and boot a local gateway
```

A local wheel is for **your** platform only. Official wheels are built in CI on
per-platform runners; do not expect a locally built Linux wheel to satisfy
`manylinux` constraints.

## Code style

- **Rust**: run `cargo fmt` on files you touched, and do not increase
  `cargo clippy` warnings. There is no rustfmt/clippy config file and CI does not
  gate formatting yet, so match the surrounding code.
- **Python**: no formatter is enforced; follow the style of the module you edit
  and keep type hints where the module already uses them.
- **TypeScript / CSS**: the UI is bundled with esmx; do not add a dependency
  without an issue that justifies it.
- **Layer boundaries**: `just check` enforces UI layering and the Rust import
  direction. If your change legitimately crosses a boundary, say so in the issue
  first — the baseline lives in `tools/dircheck/baseline.txt`.

## Submitting a patch (invited collaborators)

- One concern per pull request. Do not mix a fix, a refactor and a format change.
- Link the issue the change comes from, and explain the motivation in the body.
- Run `just test` before pushing; for UI changes, run `just build-ui` and attach a
  screenshot.
- Add a line under `## [Unreleased]` in `CHANGELOG.md` (`Added`, `Changed`,
  `Fixed`, `Removed`).
- Do not reformat or rewrite files you are not otherwise touching.
- Sign your commits: `git commit -s` (Developer Certificate of Origin). The
  sign-off certifies you have the right to submit the contribution under this
  project's license, inbound = outbound.
- Fill in the pull request checklist (see `.github/pull_request_template.md`).

## What not to change

These are maintainer-owned; a pull request touching them will be sent back:

- version numbers (`pyproject.toml`, `mdio_py/pyproject.toml`,
  `mdio_core/Cargo.toml`) and tags — releases are cut by the maintainer;
- the structure of `CHANGELOG.md` itself (add entries, do not reorganize it);
- the export/release tooling under `scripts/public_release/` (it is kept out of
  the published tree) and `.gitignore`'s public-release exceptions;
- `.github/workflows/`;
- the DuckDB extension build inputs under `mdio_core/ext/arrow/` — a rebuild must
  stay reproducible and signed the same way.

## What not to commit

`.env`, API keys or tokens, build output (`dist/`, `target/`, the generated
`mdio_py/src/mdio_py/web/client` bundle), local knowledge bases (`.mdio/`),
experiment directories (`exp_*`), and any large binary that is not a build input.
If in doubt, open an issue and ask.

## AI-assisted contributions

AI tools are welcome; the responsibility stays with you. By submitting a change
you agree that:

1. **You understand your code.** You can explain any line in it. If you cannot,
   it is not ready for review.
2. **You tested it yourself**, on a platform you can actually run. Do not submit
   code for platforms you cannot test.
3. **Changes stay small and focused.** One issue, one pull request. Large,
   multi-topic changes will be closed.
4. **Maintainers may close without review** changes that look like unverified
   generated output: hallucinated fixes, unnecessary refactors, bulk edits
   without context.

AI is a tool, not a substitute for understanding.

## Commit convention

The history follows [Conventional Commits](https://www.conventionalcommits.org/):

```
feat(worktree): support a root member in install.md
fix(cli): preserve legacy load defaults
build: switch packaging to uv and maturin
docs(community): add a security policy
test: skip live LLM tests without a key
chore(deps): drop unused direct dependencies
```

# 贡献指南（中文）

> 以下是中文要点；与英文版冲突时以英文版为准。

## 两条前提

1. **只收 issue。** 当前项目刚发布, PR 仅限受邀协作者，从 fork 开的 PR 不会被评审。获得邀请的路径：开一个高质量的 issue（带最小复现的 bug，或高质量的设计讨论）。
2. **这是发布快照，不是开发线。** 公开仓由私有开发仓按白名单导出。合到这里的补丁会先回灌到开发线，再随下一次导出重新出现；没有被回灌的改动会被下一次导出覆盖。功能开发发生在你之上游，所以想要功能请开 issue 论证，而不是直接写 PR。

## 报 bug 要带什么

版本（`mdio --version`）、安装方式、平台（Linux x86_64 / Linux arm64 / macOS arm64；**Windows 只支持 WSL2**，且 workspace 必须放在 `/home/...` 而不是 `/mnt/c`）、最小复现、期望与实际输出。安全问题不要开 issue，见 `SECURITY.md`。

## 本地开发

统一入口是构建网格（build grid），`just` 只是它的薄封装：

```bash
just doctor     # 检查工具链
just install    # uv sync（Python 3.14）+ 构建 wasm 引擎
just test       # Rust + Python 稳定子集
just check      # 层级与导入方向门禁
just wheel      # 构建本平台 wheel
just verify     # 安装该 wheel 并启动一个本地 gateway
```

工具链：Rust 1.98.0（`rust-toolchain.toml` 钉住）、Python 3.14（经 uv）、Docker（UI 打包与 DuckDB 扩展构建）。没有 `just` 时用 `python3 tools/build_grid/runner.py <target>`，支持 `--list` / `--dry-run` / `--json`。

## 测试

两条实用提醒：

- **隔离真实配置**：部分测试会读写 `~/.mdio`，用 `MDIO_HOME="$(mktemp -d)" just test-py`。只设 `MDIO_HOME`，**不要覆盖 `HOME`**（会让 cargo/rustup 缓存失效并全量重编）。
- **重活不在默认集里**：`test-omp` / `test-trinity` / `test-py-slow` 需要时单独跑；依赖 PTY、Docker、网络的测试在条件缺失时会自动跳过。
- 如果你有本地wt, 小心覆盖。

## 提交补丁（仅受邀协作者）

一次 PR 只解决一件事；链接来源 issue；推之前跑 `just test`；UI 改动跑 `just build-ui` 并附截图；在 `CHANGELOG.md` 的 `## [Unreleased]` 下加一行；不要重排无关文件；提交要带 `git commit -s` 的 DCO 签名（inbound = outbound）。

## 别动这些

版本号与 tag、`CHANGELOG.md` 的结构、`scripts/public_release/`（导出清单与同步脚本）与 `.gitignore` 的公开例外、`.github/workflows/`、`mdio_core/ext/arrow/` 的构建输入 —— 这些由维护者负责，动了会被退回。

## AI 辅助贡献

四条：能解释自己的每一行；自己在本平台真跑过；改动小而聚焦；维护者可以无评审直接关闭看起来像未验证生成内容的 PR。AI 是工具，不是理解的替代品。

## 许可与行为准则

贡献按 MIT 授权（inbound = outbound），你确认有权授权。参与行为受 `CODE_OF_CONDUCT.md` 约束；不良行为请私下报告，不要发公开 issue。
